Epic Readiness · UX redesign · Spec 1 of 4

From “a set of pages” to one guided path to “ready to submit”

The tool already does the hard part: honest verdicts, evidence, a plan with reasons. What confuses people is that the same thing has four names, the app's answers live in three places, Epic can be connected from three screens, and results don't say who they test or what to do next. This redesign keeps every capability and rebuilds the experience around one profile, one connection, one run and one report.

Base: current app on main (14af8fe), ADR-001 → ADR-016. Persona in all mockups: DermScan, a clinician mobile app integrating with Advocate Health.

Design principles

1

One source of truth: the App profile

Every answer about the app lives on one editable page. The assistant chat is just a faster way to fill it in. Plan, runs and staleness all read the profile — never a hidden last_intake.

2

One way to connect to Epic

One “Connect to Epic” flow, reused everywhere, that also tells you what to register on fhir.epic.com. “Connected” means signed in with the right profile — nothing less.

3

Every result answers three questions

What happened (one plain sentence), who it tests (your app or Epic), and what to do next (one button). Raw data sits behind “Technical details”.

4

Honest by default

Kept from ADR-009/015: missing information is never a fail, and nothing passes without proof. New: “Needs input” always names its reason, so it is never a dead end.

5

Same words everywhere

Test, Run, Result, Proof, Report. One glossary (below), enforced in UI, export, JSON and CLI.

6

The report is a deliverable

A health-system reviewer must be able to read it cold: cover, verdict, scope, method and limits, proof index with hashes. Sample-data runs are watermarked.

Glossary (one word per idea)

UseReplacesMeaning
App profileIntake, answers, “Describe your app”, last_intakeEverything the tool knows about the app: who signs in, platform, data uses, security answers, test settings. Versioned; every run records the version it used.
TestRule, check, finding (in UI)One requirement the tool can verify, e.g. CLIN-001. Has an ID, area, severity, framework(s) and who it tests.
PlanTest plan, “checks selected”The tests that apply to this profile, each with a reason. Out-of-plan tests also carry a reason.
RunAssessment, “Run N checks”One execution of the plan against Epic at a point in time.
ResultVerdict, status, findingA test's outcome in a run: Passed, Failed, Needs input, plus Not run and Out of plan for tests without a result.
Needs inputNeeds review, needs_human, Needs HumanThe tool couldn't decide and tells you why: Answer a question · Add proof · Connect a service · Refine test patient · Verify outside the app.
ProofEvidence (developer-attached)Statements, files and links you attach to a test. Kept across runs; each run snapshots hashes.
What we observedEvidence (collected), “Result” textThe data the tool collected from Epic for this test. Shown as a plain summary + technical details.
Who it testsSubject (epic_platform, app_registration…)Your app (registration, writes, stated answers) or Epic environment (Epic's own behaviour, this tool's login). Only “Your app” drives readiness.
ReadinessScore, % completePassed ÷ (Passed + Failed + Needs input) over in-plan “Your app” tests.
Verdict(new)One word for the whole app: Blocked · Fixes needed · Missing proof · Ready to submit.
ReportReport, export, Reports navThe shareable document for one run.
ConnectionIntegration, sign-in, live tokenAn external service the tool uses. Epic's connection = client ID + successful SMART sign-in (time-limited).
Out of dateStaleThe latest run no longer matches the current profile, proof, test catalog or connection.
